### 🔥 第一章 数据库概述 期末速成讲义 🔥

#### 🌟 模块一：核心概念“连连看” （理清四个名词不丢分）

考试第一关，就是让你分辨几个长得很像的英文缩写，千万别搞混了！

- **数据 (Data) vs 信息 (Information)**：数据是记录的符号，信息是数据的含义；数据是信息的载体。数据只有经过“清洗 -> 管理 -> 分析”这三步走，才能为人们找出答案，产生价值。
- **数据库 (DB, Database)**：你可以把它当成一个“大仓库”。它是长期存放在电脑里、有组织的、可共享的大量数据的集合。
- **数据库管理系统 (DBMS)**：这是用来建库、用库和管库的“超级管家软件”（比如知名的Oracle、SQL Server、MySQL等）。用户的高级指令必须靠DBMS翻译成机器代码，才能对底层数据库进行操作。
- **数据库系统 (DBS)**：这是终极“全家桶”！**必背公式：数据库系统 = 数据库 + 数据库管理系统(DBMS) + 应用开发工具 + 应用程序 + 数据库管理员(DBA)**。

#### 🐒 模块二：数据管理的“进化史” （我们是怎么走到今天的？）

数据管理经历了三个阶段，要清楚前两个阶段为啥被淘汰。

1. **人工管理阶段**：上古时代，数据不保存，随用随丢，程序和数据绑死在一起。
2. **文件管理阶段**：数据存成了文件，但毛病很多：数据共享差（同样的数据存好几份，冗余大）、数据是分离孤立的，而且**程序和数据没有真正分离（独立性差）**。
3. **数据库管理阶段（现在）**：数据由DBMS统一管理。**四大核心优点必背：整体数据结构化、数据共享度高、数据独立性高、高度的数据控制能力**。

#### 👑 模块三：全卷最重磅考点 —— 内部体系结构！

这个知识点是数据库的灵魂，简答题和选择题的重灾区！主要讲的是数据库如何做到“把用户看的、全局算的、底层存的”彻底解绑。

- **三级模式（由外向内）**：
  1. **外模式（局部视图）**：特定用户能看到的数据长啥样。这是**保证数据库安全性的有力措施**（比如普通员工只能看姓名列，不能看工资列）。一个数据库可以有多个外模式。
  2. **模式（全局逻辑）**：整个数据库总共有哪些表、什么类型，是全体用户的公共视图。**一个数据库只有一个模式**。
  3. **内模式（物理存储）**：数据在底层硬盘到底是怎么存的（比如是顺序存还是B+树存，加没加密）。**一个数据库只有一个内模式**。
- **两级映像（数据独立性的“护身符”）**：
  1. **外模式/模式映像（保证“逻辑独立性”）**：当全局的“模式”改变时，管理员调一下这层映像，用户的“外模式”就不受影响，**应用程序连一行代码都不用改**！
  2. **模式/内模式映像（保证“物理独立性”）**：当底层换了新磁盘等“内模式”改变时，调一下这层映像，上面的模式和外模式都不变，程序照样不用改！

#### 🌍 模块四：外部体系结构 （数据库系统长啥样？）

从外面看，数据库系统是怎么部署的？考点在于优缺点辨析：

- **C/S 结构（客户机/服务器）**：服务器专门负责DBMS管数据，客户机负责运行应用程序。
- **B/S 结构（浏览器/服务器）**：C/S的升级版。客户端连软件都不用装，有浏览器就行，**零维护，极易扩展**，但缺点是个性化较弱、响应速度受限。
- **分布式结构**：物理上分散在各个地域的节点，但逻辑上是一个整体。
- **并行结构**：分三种（共享内存、共享磁盘、非共享），算力强，但**弹性和容错性较差**。
- **云结构**：部署在云计算环境中，高可用、高扩展、支持多租户。

### 🔥 第二章 关系数据库 速成提纲

#### 模块一：打地基 —— 关系模型的基本概念

在关系数据库里，不要再说“表格、行、列”了，我们要用黑话（专业术语）！

- **1. 关系（Relation）= 二维表**
  - **元组（Tuple）**：表里的**一行**数据。
  - **属性（Attribute）**：表里的**一列**（比如姓名、性别），每列都要有名字。
  - **域（Domain）**：某一列的**取值范围**（比如性别的域是{男, 女}）。
  - **🔥** **必考陷阱（关系的6大性质）**：关系里**不能有重复的行**；**行和列的顺序可以随便打乱**；最重要的是**属性必须是原子的（不可再分）**，比如“工资”不能再拆成基本工资和奖金放在同一列里。
- **2. 关系模式 vs 关系（“图纸”与“大楼”的区别）**
  - **关系模式（Schema）**：是表的“结构图纸”，规定了表名、列名和数据类型。它是**静态的、稳定的**。
  - **关系（值）**：是表里真金白银的数据。由于我们会不断增删改数据，所以它是**动态的、随时间变化的**。
- **3. 码（Key）—— 找人的唯一凭证（绝对重点！）**
  - **候选码**：能**唯一标识**一行数据，且没有任何多余列的属性组。比如“学号”或者“身份证号”。
  - **主码（Primary Key）**：如果有多个候选码，数据库管理员挑一个最顺眼的作为主码。
  - **主属性/非主属性**：只要被包含在任何一个候选码里的列，就是主属性；否则就是非主属性。
  - **外码（Foreign Key）**：表里的一列，它虽然不是自己的主码，但却是**别人表里的主码**。外码的作用就是把两张表**“串”**起来！

#### 模块二：数据怎么查？—— 查询语言

- 查询语言不用你写具体的过程，你只需告诉系统“你要什么”（高度非过程化）。主要分三类：**关系代数**（用集合运算找）、**关系演算**（用谓词逻辑找）、**SQL语言**（介于两者之间，以后实战都用它）。

#### 模块三：大轴戏 —— 关系代数（必考计算题！）

这部分是把表当成集合，用数学符号做运算。**记住下面这几个“切蛋糕”的动作！**

**1. 传统的集合运算（要求两张表的列长得一样）**

- **并（$\cup$）**：两张表合在一起，**自动去掉重复行**。
- **交（$\cap$）**：找出两张表里一模一样的行。
- **差（$-$）**：在表A里，把属于表B的行抠掉。
- **笛卡尔积（$\times$）**：表A的所有行和表B的所有行**无脑两两组合**（如果A有3行，B有4行，结果就是12行）。

**2. 专门的关系运算（核心拿分项！！！）**

- **选择（$\sigma$ —— 选行）**：
  - **动作**：横向切蛋糕。根据条件把满足的**行**挑出来。
  - **例题**：挑出年龄小于19岁的学生 $\rightarrow$ $\sigma_{Sage<19}(Student)$。
- **投影（$\pi$ —— 选列）**：
  - **动作**：纵向切蛋糕。把需要的**列**抠出来。
  - **🔥** **必考陷阱**：投影之后，如果出现了重复的行，**系统会自动把重复行删掉**！（比如查询全校有哪几个系，多个相同的'CS'系会被去重只留一个）。
- **连接（$\bowtie$ —— 拼表）**：
  - **动作**：把两张表按一定条件拼成一张大表。
  - **自然连接**：最常用的连接！它会自动找到两张表里**同名的列**，把值相等的行拼在一起，并且**自动把重复的同名列去掉一列**。
  - **悬浮元组与外连接**：自然连接时，有些行匹配不到对象（比如某个学生没选课），就被残忍抛弃了，这些叫**悬浮元组**。如果想把他们捞回来：
    - **左外连接**：保住左边表的所有行，右边匹配不到的填空值（NULL）。
    - **右外连接**：保住右边表的所有行，左边填空值。
- **除法（$\div$ —— 找“全部”）**：
  - **动作**：专门用来解决带有**“全部”、“所有”**字眼的查询。
  - **例题**：找同时选修了1、2、3号课程的学生，就是用包含选课记录的表 去除以（$\div$） 包含1、2、3号课程的表。

#### 🌟 模块一：全局观 —— SQL到底是个啥？

首先，SQL（结构化查询语言）是你和数据库沟通的唯一“普通话”。不管你用什么数据库，这套语言都通用。

**1. SQL的核心四大件（必背分类）**：

- **DDL（数据定义语言）**：负责“建大楼”。关键字：`CREATE`（建）、`ALTER`（改）、`DROP`（删）。
- **DML（数据操纵语言）**：负责“搬砖”，管数据的增删改。关键字：`INSERT`（增）、`UPDATE`（改）、`DELETE`（删）。
- **DQL（数据查询语言）**：负责“找东西”，也就是核心重头戏。关键字：`SELECT`。
- **DCL（数据控制语言）**：负责“发门禁”，管权限。关键字：`GRANT`、`REVOKE`。

**2. 我们操作的“沙盒”**：

整章的所有实战，都在围绕一个“学生选课系统”的5张核心表展开：`Student`（学生表）、`Course`（课程表）、`SC`（选课表）、`Teacher`（教师表）、`TC`（授课表）。以后遇到看不懂的字段，就在脑子里回想这5张表！

------

#### 🔨 模块二：数据定义（DDL）—— 怎么建库建表？

考试中，建表语句是最基础的填空题或简答题。

**1. 建表的基本语法**：

使用 `CREATE TABLE`，你需要注意**主码（PRIMARY KEY）**和**外码（FOREIGN KEY ... REFERENCES ...）**的绑定。

> **💡** **冲刺提示**：注意常见数据类型，比如 `VARCHAR(n)` 是变长字符串，`INT` 是整数，`DATE` 是日期。

**2. 修改表与删除表**：

- 加新列：`ALTER TABLE 表名 ADD 列名 数据类型;`
- 删旧列：`ALTER TABLE 表名 DROP COLUMN 列名;`
- 删整个表：`DROP TABLE 表名;`

**3. 索引（Index）—— 让查询飞起来的“目录”**：

- **聚簇索引（CLUSTERED INDEX）**：这绝对是高频考点！聚簇索引不仅建了目录，还把硬盘里的数据直接按照这个顺序物理排列了。
- **什么时候建聚簇索引？（必背三种情况）**：
  1. 经常用这个列来排序；
  2. 需要返回一个范围内的大量数据；
  3. 这个列的内容重复性很大（比如“部门号”）。

#### 🧱 模块三：数据更新（DML）—— 增与删

这部分最简单，记住两个公式拿分：

- **插入数据**：`INSERT INTO 表名 VALUES ('值1', '值2'...);`。
- **删除数据**：`DELETE FROM 表名 WHERE 条件;`。（如果不加WHERE，就会把整张表的数据全清空！）

#### 🔎 模块四：数据查询（DQL）—— 试卷压轴题重灾区！

全卷最贵的分数都在这里，`SELECT` 查询千变万化，但万变不离其宗。咱们按难度分级攻破！

**Level 1：单表查询（基础捞分项）**

- **万能句式**：`SELECT ... FROM ... WHERE ... GROUP BY ... HAVING ... ORDER BY ...`。
- **模糊查询**：用 `LIKE` 加上通配符 `%`。比如找所有姓林的学生：`WHERE Sname LIKE '林%'`。
- **分组过滤（核心易错点！）**：`WHERE` 和 `HAVING` 的区别是什么？
  - `WHERE` 是在**分组前**起作用，筛选每一条原始数据；
  - `HAVING` 是在 `GROUP BY` **分组后**起作用，筛选的是“组”。而且它们执行的顺序是先 `WHERE` -> 再 `GROUP BY` -> 然后聚合计算 -> 最后 `HAVING`。

**Level 2：连接查询（跨表找人）**

当你要的数据在两张或以上的表里，就要用连接查询。

- **自身连接**：自己连自己怎么办？比如“找和刘晨同系的学生”。诀窍是**给表起别名**，如 `FROM Student S1, Student S2`，然后用 `S1.Sdept = S2.Sdept` 连接。

**Level 3：嵌套查询（套娃魔法）**

查询里面包着查询，由内向外执行。

- **IN 操作符**：内层查出一个集合，外层看在这个集合里有没有。
- **ALL 操作符**：`< ALL` 表示要比集合里面**最小的那个还要小**。
- **EXISTS 操作符**：只管“有没有”，找到了就返回 True。
- **🔥** **终极必考大招：没有全称量词（$\forall$）怎么办？**

SQL里没有“全部”这个词，所以当我们遇到**“查询选修了全部课程的学生”**时，必须用“双重否定表肯定”的逻辑转换！

> 翻译公式：“选了全部课程” = **“不存在一门课，这个学生没有选”**。
> 对应代码模板：`NOT EXISTS ( SELECT * FROM Course WHERE NOT EXISTS (该学生选了这门课的条件) )`。

**Level 4：集合操作（拼积木）**

如果你有两个查询结果，可以通过 `UNION`（并集）拼在一起。注意 `UNION` 会自动去重，如果你想保留重复的，要用 `UNION ALL`。

------

#### 🎭 模块五：视图（View）—— 定制版的假表

视图不是真实的表，它是一个“虚拟表”，就像是你透过窗户（View）看外面的风景。

- **怎么建视图？** `CREATE VIEW 视图名 AS SELECT ...`。
- **考点预警（WITH CHECK OPTION）**：如果在建视图时加了这句话，以后通过视图修改数据时，系统会严格检查新数据是否符合视图的条件（比如视图只看年龄<20岁的，你如果想插入一个25岁的就会被拒绝）。
- **易错细节**：如果在视图的 SELECT 里用了聚合函数（如求平均成绩 `AVG(Grade)`），那么创建视图时**必须强制给视图的列起名字**！

### 🔥 **第四章 关系数据库编程 内部速成提纲** 🔥

#### **一、 打地基：Transact-SQL（T-SQL）语法基础**

传统的SQL只能做查询，而T-SQL是带有控制流的“升级版编程语言”。

- **变量与常量**：变量分两种。
- **常用运算符**：除了加减乘除，重点记住**逻辑运算符**（`AND`、`OR`、`NOT`、`BETWEEN`、`IN`、`EXISTS`等）和**字符串连接符**（用`+`号把两个字符串连起来）。
- **四大控制结构（必考逻辑）**：
  - `BEGIN...END`：打包语句块，相当于大括号 `{}`，把多条语句作为一个整体执行。
  - `IF...ELSE`：条件分支，条件为真执行IF后面语句，为假执行ELSE后面语句。
  - `WHILE`：循环结构，满足条件时重复执行，可以配合 `BREAK`（跳出循环）和 `CONTINUE`（跳过本次循环）使用。
  - `CASE`：多分支选择（简单格式和搜索格式），根据不同条件返回特定的值。

#### **二、 逐行处理神器：游标（Cursor）**

普通的SELECT查询返回的是一堆数据（集合），但程序通常喜欢一行一行处理。**游标就是集合操作与单行记录处理之间的“桥梁”**。

- **游标操作四部曲（核心操作流）**：
  1. **定义**：`DECLARE 游标名 CURSOR FOR 查询语句`（把一个SELECT结果集与游标绑定）。
  2. **打开**：`OPEN 游标名`。
  3. **提取**：`FETCH NEXT FROM 游标名 INTO @变量名`（把游标当前指向的一行数据拿出来，存到局部变量里）。通常配合 `@@FETCH_STATUS = 0` 来循环判断是否成功取到了下一行数据。
  4. **关闭与删除**：用完后必须 `CLOSE 游标名`（关闭），并彻底释放内存空间 `DEALLOCATE 游标名`（删除）。

#### **三、 数据库的高效代码块：存储过程（Stored Procedure）**

把一大段常用的SQL代码写好并存储在数据库服务器里，用的时候直接一句话调用。

- **四大核心优势**：允许模块化程序设计、执行速度更快、极大减少网络流量消耗、能作为一种安全机制使用。
- **如何操作**：
  - **创建/修改/删除**：分别对应关键字 `CREATE PROC`、`ALTER PROC`、`DROP PROC`。
  - **参数传递**：可以带有输入参数（给它传值）、带有默认值的参数，甚至带有**输出参数**（带 `out` 或 `output` 关键字，用于把值返回给调用者）。
  - **执行**：使用 `EXEC 过程名` 即可一键运行。

#### **四、 自定义函数（Function）**

当你需要特定计算或返回特定格式时，可以自己编写函数，不支持输出参数，但按返回值类型可分为三类：

- **标量函数**：只返回一个单一的具体数据值（例如返回一个整数或字符串）。
- **内联表值函数**：返回一张表，内部由一个简单的SELECT语句定义，**它相当于一个“可以传参数的视图”**，能用来替代视图。
- **多语句表值函数**：同样返回一张表，但在函数体内部可以通过多条SQL语句（如INSERT）来慢慢拼凑和定义这张表的数据。

#### **五、 外部应用连接桥梁：ODBC 与 JDBC（连接实操重点）**

这是让外部程序（如Java开发的系统）连上底层数据库的统一接口。

- **ODBC（开放式数据库互连）**：微软主导的一套标准。应用不再直接连数据库，而是：**应用程序 -> ODBC管理器 -> 驱动程序管理器 -> ODBC驱动程序 -> 数据库**。靠换驱动程序就能连各种不同的数据库。
- **JDBC（Java数据库连接）**：由Java API和JDBC驱动接口组成，是Java程序连数据库的基础。
  - **配置与开发核心步骤**：
    1. **配置SQL Server**：启用“SQL Server和Windows身份验证模式”（混合模式），启用并设置超级管理员 `sa` 的密码。
    2. **网络配置**：在SQL Server配置管理器中开启TCP/IP协议，**必须将TCP端口设为** `**1433**`，并将IP地址设为 `127.0.0.1`。
    3. **导入驱动与编程**：下载JDBC驱动包并加入到项目的CLASSPATH中。然后在Java代码中利用 `DriverManager.getConnection()` 建立连接，并通过 `Statement` 对象执行SQL语句。

### 🔥《第五章 数据库安全与保护》期末速成讲义

#### 第一部分：安全性（Security）—— 如何“防外人”

安全性的核心是防止未经授权的用户存取数据。

- **考点1：自主存取控制 (DAC) —— 权力的下放与收回**
  - **授权 (GRANT)**：管理员或属主把权限给用户。**冲刺必考**：如果带上 `WITH GRANT OPTION` 尾巴，说明该用户不仅自己能用，还能把这个权限继续“转包”给别人。
  - **回收 (REVOKE)**：把给出去的权限收回来。**冲刺必考**：如果回收带 `WITH GRANT OPTION` 的权限，必须加上 `CASCADE`（级联回收），即把转包出去的底层权限一锅端掉。
  - **角色 (Role)**：为了不给用户一个一个授权，可以建一个“角色”（权限打包集合），把权限赋予角色，再把角色挂接给多个用户，方便批量管理。
- **考点2：强制存取控制 (MAC) —— 军方级别的严格管控**
  - 适用于有严格密级分类的部门（如军事、政府）。
  - **冲刺必考口诀：“向下读，平级写”**。只有当主体的许可证级别 **大于或等于** 客体的密级时，才能“读”；**等于** 客体密级时，才能“写”。
- **考点3：视图机制保密**
  - 通过给不同用户定义不同的“视图”，把敏感数据隐藏起来。比如员工只能通过视图看到公共信息，看不到工资列。

#### 第二部分：完整性（Integrity）—— 如何“防自己人犯错”

完整性是为了保证数据库中的数据是**正确、相容、一致**的，符合现实世界的语义。

- **考点1：三大完整性规则（绝对重点！）**
  - **实体完整性**：对应 `PRIMARY KEY`（主键）。主键的属性**绝对不能为空，且必须唯一**。系统底层一般会自动建索引（如B+树）来快速查重。
  - **参照完整性**：对应 `FOREIGN KEY`（外键）。如果你引用了别人的表，你的外键值必须在别人的主键里能找到，或者干脆为空。如果别人表里的记录删了或改了，系统有三种反应：**拒绝执行（默认）、级联操作（跟着一起删/改）、设置为空值**。
  - **用户自定义完整性**：针对特定业务的约束。比如成绩必须在0-100之间（`CHECK`），姓名不能重复（`UNIQUE`），或者必须填（`NOT NULL`）。
- **考点2：大招“触发器 (Trigger)”**
  - **定义**：它是一种特殊的存储过程，不用人手工调用，一遇到 `INSERT`、`UPDATE`、`DELETE` 事件就自动触发，用于实现超级复杂的完整性业务规则。
  - **冲刺必考：两张神级虚拟表**。
    - **Inserted 表**：记录**新增**的数据，或者更新后的**新数据**。
    - **Deleted 表**：记录**被删除**的数据，或者更新前的**旧数据**。

#### 第三部分：并发控制（Concurrency）—— 如何“防多用户打架”

数据库是大家共享的，如果不加控制同时修改数据，就会乱套。

- **考点1：事务 (Transaction) 的四大神兽 (ACID)**
  - **原子性**（要么全做要么都不做）、**一致性**、**隔离性**、**持久性**。
- **考点2：并发操作的三大惨案（必考概念辨析）**
  - **1. 丢失修改**：你和我都去改同一条数据，你提交的结果把我的结果覆盖了，我白干了。
  - **2. 脏读**：我读了你修改的数据，结果你突然反悔“撤销”了，那我读到的就是不曾存在的“脏数据”。
  - **3. 不可重复读 & 幻像读**：我先后两次去读同一批数据，结果你中途插手改了（或删了、新增了）数据，导致我两次读出来的数据对不上。
- **考点3：封锁与两段锁协议**
  - 解决并发的核心是加锁。**两段锁协议**是并发事务正确调度的准则。
  - **冲刺必背**：遵循两段锁协议的并发调度一定是**可串行化的**（即结果是正确的），但它**依然可能会发生死锁**！

#### 第四部分：恢复机制（Recovery）—— 如何吃“后悔药”

系统崩溃了、磁盘坏了、数据错了怎么办？

- **考点1：两大保命法宝**
  - **数据转存**：就是定期的备份（海量/增量、静态/动态）。
  - **登记日志文件**：记录事务的一举一动。**铁律：必须先写日志，再修改数据**。
- **考点2：故障恢复策略（动作大赏）**
  - **事务故障**：不用重启，直接反向扫描日志，执行**逆操作 (Undo)**。
  - **系统故障（死机了）**：重启系统时，正向扫描日志，把已经提交的事务放入 **重做队列 (Redo)** 重新执行一遍，把未提交的事务放入 **撤销队列 (Undo)** 撤回。
  - **介质/病毒故障**：需要装入最新的备份文件，再利用日志文件对提交的事务进行 Redo 重放。
- **考点3：检查点 (Checkpoint) 机制**
  - 相当于存档点。系统恢复时不需要把厚厚的日志从头翻到尾，只从最后的检查点开始即可，大大节省了 `Redo` 操作的时间。

### 🔥冲刺讲义：第6章 规范化理论速成提纲

#### 核心模块一：为什么要“规范化”？（表格生病了有什么症状？）

一个设计不好的关系模式（表格），会得四种“病”：

1. **数据冗余度大**：比如一门课有100个学生选，这门课的任课老师名字就要在表里重复存100次，白白浪费空间。
2. **插入异常（插不进去）**：比如学校刚成立一个新系，还没招学生，由于学生学号是主码（不能为空），这个系的信息居然无法存入数据库。
3. **删除异常（删得太猛）**：某门课的学生全都毕业被删除了，结果连带着这门课和任课老师的信息也跟着从数据库里消失了。
4. **修改复杂（更新异常）**：某个老师改名了，所有选他课的学生记录全都要跟着挨个改一遍，极易出错。

**讲师大白话**：规范化（Normalization）就是通过“拆表”（模式分解），消除不合适的数据依赖，把复杂的大表拆成简单的小表，做到“一事一地”（一个表只管一件事）。

------

#### 核心模块二：判断健康程度的标准——“范式”（Normal Forms）

范式（NF）就是表格健康的等级，等级越高，毛病越少。低级范式可以通过“分解”升级为高级范式。

- **1NF（第一范式）—— 及格线**：
  - **要求**：表里的每一个属性（列）都必须是**不可再分**的基础数据项。
  - **大白话**：表里不能有“表中有表”的嵌套结构，这是关系数据库的最起码要求。
- **2NF（第二范式）—— 消除“部分依赖”**：
  - **要求**：在1NF基础上，每一个非主属性都必须**完全依赖**于码，不能只依赖码的一部分。
  - **大白话**：如果主码是由两个列（比如 学号+课程号）联合组成的，那么其他列必须同时依赖这两个列，不能只跟学号有关或者只跟课程号有关。
- **3NF（第三范式）—— 消除“传递依赖”**：
  - **要求**：在2NF基础上，消除非主属性对码的**传递函数依赖**。
  - **大白话**：表里不能有 A决定B，B又决定C 的连带关系。比如“学号->系名->系主任”，系主任实际上是通过系名传递依赖于学号的，这就不符合3NF。
- **BCNF（Boyce-Codd范式）—— 3NF的加强版**：
  - **要求**：在1NF基础上，任何属性（包括主属性）都不能对码有部分依赖和传递依赖。更直观的定义是：**只要有 X->Y 的依赖关系，X 就必定包含了候选码**。
  - **大白话**：连主键（码）内部的各个列之间，也不能互相依赖、互相“打架”。
- **4NF（第四范式）—— 消除多值依赖**：
  - **要求**：处理“一对多对多”的复杂情况，消除非平凡且非函数依赖的**多值依赖**（X->->Y）。

------

#### 核心模块三：考试必考的“三大硬核计算题”

这部分是期末考试拿分的大头，请务必掌握以下三种算法操作：

#### 考点1：求属性闭包（X+）

- **含义**：给你一个属性集合X，根据已知的规则（函数依赖集F），看你能顺藤摸瓜推导出多少其他的属性。
- **解题套路（算法6.1）**：像滚雪球一样，一开始雪球只有X本身；然后去扫描所有的依赖规则，只要规则的左边完全包含在你的雪球里，就把右边的属性也粘到雪球上；不断重复，直到雪球变大到不能再变大为止。

#### 考点2：神技！快速找“候选码”

给你一堆属性U和依赖关系F，怎么找出候选码？讲师教你把属性分为四类（L/R/N/LR），直接秒杀：

1. **L类（只在箭头左边出现）**：它肯定是候选码的一部分！
2. **R类（只在箭头右边出现）**：它**绝对不可能**在任何候选码里！
3. **N类（左右都没出现过）**：它也是孤家寡人，必须强行拉入候选码中！
4. **LR类（左右都出现过）**：这是墙头草。

- **秒杀大招**：先把L类和N类的属性拿出来，求一下它们的闭包（滚雪球）。如果一下子把所有属性都推导出来了，那它们就是**唯一候选码**！（详见PPT例6.4、例6.5）

#### 考点3：求最小函数依赖集（最小覆盖 Fm）

为了让规则最精简，需要经过“减肥三步曲”：

1. **右边单一化**：把所有箭头右边拆成单个属性。比如 `A -> BC` 拆成 `A -> B` 和 `A -> C`。
2. **删多余规则**：尝试遮住某一条规则，看看用剩下的规则还能不能推导出这条规则。如果能，说明它是废话，删掉！
3. **删左边多余属性**：如果规则左边有两个以上属性（如 `AB -> C`），试着遮住A，看仅凭B能不能推出C；如果能，说明A是多余的，把A踢掉！

------

#### 核心模块四：终极手段——模式分解

如果表格生病了，我们就把它拆开（分解）。但拆表是有讲究的，不能瞎拆：

1. **无损连接性**：拆开的表以后如果做自然连接合并起来，必须和原来的表**一模一样**，不能丢信息，也不能多出原本没有的假数据（如PPT中因错误分解多出了3条幽灵数据）。判断方法是使用画表格的算法。对于分解成两个表的情况有一个神仙定理：如果两个表相交的公共属性，能够推导出其中一个表的剩余属性，那就是无损的。
2. **保持函数依赖**：拆分后，原来表里的那些业务规则（依赖关系）最好还能在各自的小表里找到归宿，不要丢失。

**考试重要结论**：

- 如果只要求“无损连接”，任何模式都可以一直分解到最高级的 BCNF。
- 如果只要求“保持函数依赖”，我们总是可以分解到 3NF，但**不一定**能达到 BCNF。
- 如果又要“无损连接”又要“保持函数依赖”，最高也就只能保证达到 3NF。

### 🔥冲刺讲义：第7章 数据库设计速成提纲

#### 🌟 核心总纲：数据库设计的六大步

数据库设计本质上是软件工程的一部分，它是一个不断推进、不满意随时退回重做的过程。**必背的六个阶段是：**

1. 需求分析 $\rightarrow$ 2. 概念结构设计 $\rightarrow$ 3. 逻辑结构设计 $\rightarrow$ 4. 物理设计 $\rightarrow$ 5. 数据库实施 $\rightarrow$ 6. 运行和维护。

**(考试重点：你要清楚哪一步该干什么，哪些人参与。比如系统分析人员贯穿始终，而程序员主要在实施阶段才大量介入。)**

------

#### 🥇 阶段一：需求分析（最困难、最耗时的一步）

这里我们不仅要弄清楚用户需要什么，还要明确系统边界。

- **方法利器**：最常用的是**自顶向下的结构化分析方法（SA）**，就像画一棵树一样，把大系统一层层往下分解，直到变成能直接处理的“叶子”。
- **辅助工具**：文字说不清的，通常配合**数据流图（DFD）和数据字典**来辅助分析和表达。

#### 🥈 阶段二：概念结构设计（核心考点：画E-R图！）

这一步是把用户的业务需求，变成一种连不懂电脑的老板也能看懂的“信息模型”。

- **四大策略**：自顶向下、自底向上、逐步扩张、混合策略（先自顶向下分析需求，再自底向上设计结构）。
- **三大基本元素**：
  1. **实体**（矩形）：客观存在的事物，比如“学生”、“商品”。
  2. **属性**（椭圆）：实体的特征，比如“姓名”、“价格”。
  3. **联系**（菱形）：实体间的关系，可以自带属性。
- **必考的“联系类型”**：
  - **一对一（1:1）**：例如一个观众只坐一个座位，一个座位只有一位观众。
  - **一对多（1:n）**：例如一个部门有多个职工，但职工只属于一个部门。
  - **多对多（m:n）**：例如一个项目有多个职工参与，一个职工也参与多个项目。
- **局部E-R图集成**：合并大家画的子图时，一定会打架（冲突）。**必须解决的三大冲突**是：属性冲突（比如单位不统一）、命名冲突（同名异义或异名同义）和结构冲突。解决冲突并消除不必要的冗余数据后，就得到了最终的“基本E-R图”。

#### 🥉 阶段三：逻辑结构设计（重中之重：E-R图转关系模式）

这一步要把画好的E-R图，翻译成数据库真正能建表的“关系模式”。**以下转换规则必背，大题常考：**

1. **实体的转换**：直接变成一个关系（表），实体的属性就是表的列，实体的码就是表的主键。
2. **1:1 联系**：可以单独建一张表，也可以合并到任意一端的实体表中（把另一端的主键拉过来当外键）。
3. **1:n 联系**：可以单独建表，但**最推荐的做法**是把“1”这一端的主键，塞到“n”那一端的实体表里当新属性。
4. **m:n 联系**：**必须单独建一张新表！**新表的列由相连实体的码和联系自身的属性组成，主键是两个实体码的组合。
5. **多元联系（3个以上实体）**：也要单独建一张新表，把所有相连实体的主键拉进来组合成新主键。

**(转换完后，记得用关系规范化理论（范式）来优化它们，消除冗余依赖！)**

#### 🏅 阶段四：物理结构设计（到底怎么存进硬盘？）

逻辑表设计好后，现在要决定怎么把它们存进底层的硬盘里，以最快的方式被查到。

- **确定分布**：是集中存还是分散存（分布式管理）。
- **确定存储结构与访问方式**：可以用顺序、哈希或B+树存储。这里重点考**“聚簇索引（Cluster）”**！
  - **建聚簇原则**：字段值要相对稳定（少修改）、主要用于查询或连接、对应的重复值既不能太多也不能太少。

#### 🎖️ 阶段五 & 六：实施与运行维护（落地与售后）

- **数据库实施**：这时候才真正开始写SQL代码（DDL定义结构），把数据导进去（载入），并编写和调试应用程序，进行试运行。
- **运行和维护**：系统上线不代表结束！DBA（数据库管理员）要长年累月地进行备份恢复、安全控制、性能监控改进，以及在必要时对数据库进行重组和重构。

### 🔥 冲刺讲义：第8章 NoSQL数据库 速成提纲

#### 🌟 模块一：NoSQL到底是个啥？为什么火？

很多同学以为NoSQL是“反SQL”，其实它的全称演变至今，代表的是 **“Not only SQL（不仅是SQL）”**。它认为关系库和非关系库各有优缺点，谁也无法取代谁。

**为什么传统关系数据库（RDBMS）在Web 2.0时代不香了？（必考三大原因）**：

1. **撑不住**：无法满足海量数据的管理需求。
2. **顶不住**：无法满足数据高并发的读写需求。
3. **扩不动**：传统数据库很难“横向扩展”（加几台便宜电脑就提升性能），且为了保证严格的事务，可用性受到了限制。

**讲师大白话**：Web2.0网站（如发微博、看网页）根本不需要传统数据库那么严格的事务和复杂的SQL查询，这时候NoSQL就应运而生了。

#### ⚔️ 模块二：门派大比拼 —— RDBMS vs NoSQL

考试极爱出这两者的对比选择题或简答题！

- **一致性**：RDBMS是**强一致性**（严格遵守ACID事务），NoSQL是**弱一致性**（只求最终一致）。
- **模式（Schema）**：RDBMS是**固定**的（必须先建表、定规矩），NoSQL是**灵活**的（没规矩，随便存）。
- **扩展性**：RDBMS很难横向扩展，NoSQL**横向扩展能力极好**。
- **当前结论（混合架构）**：它们彼此无法取代！现在的公司大都采用**混合架构**。比如亚马逊，临时性的“购物车”数据用NoSQL键值库，而核心的“订单流水”依然老老实实存在关系数据库里。

#### 🛡️ 模块三：NoSQL的四大神兵利器（连线/填空题必考！）

NoSQL不是一种数据库，而是一大类。你要牢记这四大分类及其代表产品（PPT里给出了极其形象的比喻）：

1. **键值（Key-Value）数据库**：代表产品是 **Redis**。
   - **特点**：就像孙悟空的**“金箍棒”**，结构最简单，速度极快。主要用于**内容缓存**（如购物车、会话）。缺点是只能通过键找值，无法做复杂关联查询。
2. **文档（Document）数据库**：代表产品是 **MongoDB**。
   - **特点**：就像**“瑞士军刀”**，数据是“自包含”的（如JSON格式）。非常灵活，适合需要面向文档存储的互联网应用。
3. **列族（Column-Family）数据库**：代表产品是 **HBase**、Cassandra。
   - **特点**：就像**“大象兵”**，依托Hadoop等大数据的生态环境，具有极强的分布式扩展能力，专治几百TB的海量数据。
4. **图（Graph）数据库**：代表产品是 **Neo4J**。
   - **特点**：专门用来处理具有**高度相互关联关系**的数据。最典型的应用场景就是**社交网络（朋友圈图谱）、推荐系统**等。

#### 💎 模块四：本章灵魂 —— NoSQL的三大理论基石（压轴重灾区！）

这部分是重中之重，必须拿下三个英文缩写：**CAP** 和 **BASE**。

**基石一：CAP 定理（鱼和熊掌不可兼得）**

一个分布式系统，最多只能同时满足以下三个指标中的**两个**：

- **C（Consistency / 一致性）**：所有节点在同一时间的数据必须一模一样。
- **A（Availability / 可用性）**：系统必须能快速响应用户请求，不管成功还是失败。
- **P（Partition Tolerance / 分区容忍性）**：当网络断开（部分节点失联）时，系统还要能正常运行。
- **必背考点**：传统关系库选择了 **CA**（放弃了分区容忍性）；而多数NoSQL为了保证互联网系统的可用性和容忍性，选择了 **CP 或 AP**（也就是放弃了强一致性）。

**基石二：BASE 模型（对传统ACID的颠覆）**

- **BA（Basically Available / 基本可用）**：允许系统部分出故障，但主体功能依然可用。
- **S（Soft-state / 软状态）**：允许数据在一段时间内不同步，具有一定的滞后性。
- **E（Eventual consistency / 最终一致性）**：虽然中间允许不同步，但经过一段时间后，数据最终必须达到一致的状态。

**基石三：最终一致性**

为了达到最终一致性，可以根据访问时间分为几种：例如**“因果一致性”**、**“读己之所写”一致性**（自己更新的数据，自己下次一定能读到最新的）、**单调读一致性**等。

#### 🚀 模块五：未来的演进 (NewSQL)

随着大数据时代发展，架构呈现多元化。现在不仅有OldSQL（传统事务）、NoSQL（互联网海量数据），还出现了一种试图融合两者优点的新型数据库——**NewSQL**。

### 🔥 冲刺讲义：第9章 分布式数据HBase 速成提纲

#### 🌟 模块一：HBase是个啥？（必考对比题！）

HBase是谷歌BigTable的开源实现，专门用来存非结构化和半结构化的海量数据。考试最爱考它和传统关系数据库（RDBMS）的区别：

- **数据类型**：传统库有整型、字符型等；HBase极简，**所有数据全当成未经解释的字符串（Byte数组）存**，没那么多规矩。
- **数据操作**：传统库爱做复杂的多表连接（JOIN）；HBase**只有简单的增查删**，绝不搞复杂的表间关系。
- **存储模式（核心！）**：传统库是“按行存”的；**HBase是“按列存”的**（面向列），空列完全不浪费空间。
- **可伸缩性**：传统库很难加机器扩容；HBase天生支持**灵活的水平扩展**，加几台机器就能提升性能。
- **吃“后悔药”的方式**：传统库更新数据是直接覆盖旧值；**HBase不覆盖旧值，而是生成一个新版本（带时间戳）**，旧数据依然保留。

#### 🗺️ 模块二：数据模型 —— 四维坐标系（绝对重点！）

在HBase里找一个具体的数据（单元格），不能只靠“行和列”了，必须靠一个**“四维坐标”**：

1. **行键（Row Key）**：每行的唯一标识，类似于主键。
2. **列族（Column Family）**：一张表分为几个大类，**列族是基本的访问控制单元**，同一个列族的数据在物理上存在一起。
3. **列限定符（Column Qualifier）**：列族下面的具体列名。
4. **时间戳（Timestamp）**：因为HBase会保留多个版本的数据，所以必须靠时间戳来区分你要看哪一次的旧数据。

> **🎓 讲师大白话**：`[行键, 列族, 列限定符, 时间戳]` 这四个词死死绑在一起，就能精准定位到一个数据。

#### 🏛️ 模块三：系统架构 —— 谁在干活？（填空/选择重灾区）

HBase系统有四个核心大将，各司其职，千万别记串了：

1. **Zookeeper**：大管家！负责选出Master，监控谁宕机了。**客户端要找数据，也是先问Zookeeper，而不是去问Master**。
2. **Master（主服务器）**：高管！不干脏活累活，只负责管理表结构、分配数据块（Region）给手下、实现负载均衡。
3. **Region Server（Region服务器）**：苦力打工人！HBase最核心的模块，真正负责存数据，**直接响应用户的读写请求**。
4. **客户端（Client）**：包含访问接口，会在缓存里记住数据在哪，下次直接找对应服务器。

#### 🔪 模块四：数据怎么切？怎么找？（寻址机制）

- **切蛋糕（Region分裂）**：表太大了怎么办？HBase会把它横向切成一块块的，叫作**Region**。随着数据变多，一个Region还会自动分裂成两个。每个Region服务器负责管理几十到上千个Region。
- **找数据（两层寻址新方法）**：0.96版本后采用了新找法。
  1. 客户端先找 **Zookeeper**，问出 `hbase:meta` 表在哪台服务器。
  2. 连接那台服务器，查 `hbase:meta` 表，这个表里记着你要找的“行键”归哪个Region管，以及那个Region在哪个打工人（服务器）手里。
  3. 直连那个打工人（Region Server）拿数据。

#### ⚙️ 模块五：底层运行机制（内部黑盒）

Region服务器内部是怎么工作的？（常考简答题）

- **写数据流程**：用户写数据 $\rightarrow$ **必须先写进 HLog（日志文件，为了防崩溃）** $\rightarrow$ 再写入内存缓存（MemStore） $\rightarrow$ 缓存满了就“刷写”到磁盘上（生成 StoreFile）。
- **StoreFile大合并**：每次刷写都会生成新文件，文件太多找起来慢，系统会偷偷把多个小文件**合并（Compact）成一个大文件。大文件如果太大，又会触发分裂（Split）**，变成两个子Region。
- **HLog 保命机制**：如果某台服务器突然断电死机了，内存里的数据还没存盘怎么办？别怕，系统会读取之前存的 **HLog（预写式日志）**，把操作重新做一遍，完美恢复数据。

#### 💻 模块六：实战操作与 Shell 命令（必背代码词汇）

考试极有可能让你写出简单的HBase命令，记住以下几个动作：

- **建表**：`create '表名', '列族名'` （注意：HBase不需要先建数据库，直接建表）。
- **增/改数据**：`put '表名', '行键', '列族:列', '值'` （put一次只能改一个格子，且增和改都是它）。
- **查一行**：`get '表名', '行键'`。
- **看全表**：`scan '表名'`。
- **删表“两步走”**：必须先 `disable '表名'`（让表失效），然后才能 `drop '表名'`（彻底删除）。

### 🔥 冲刺讲义：第10章 MongoDB 速成提纲

#### 🌟 模块一：揭开MongoDB的面纱（它是谁？能干嘛？）

- **核心特点**：MongoDB 是面向**文档（Document）**存储的，数据结构非常松散，采用的是一种叫 **BSON（Binary-JSON）** 的格式。
- **讲师大白话**：BSON就像是我们常见的JSON格式的“二进制升级版”，它支持把复杂的数组、对象直接嵌套在一条数据里存起来，非常轻量且高效。
- **能干嘛（应用场景）**：非常适合存那些结构不固定、海量且需要高效率访问的数据。比如：**社交场景**（存朋友圈、附近的人）、**游戏场景**（存用户不断变化的装备和积分）、**物流订单**、**物联网设备日志**以及**视频直播互动**。

#### ⚔️ 模块二：必考连线题！MongoDB vs 传统关系数据库

- **🔥** **核心优势案例（博客系统）**：在传统数据库中，一篇博客的内容、评论、投票可能需要建**3张不同的表**，查询时还要做极其消耗性能的“连接（JOIN）”操作；而在MongoDB中，因为支持“嵌套”，你可以**把评论和投票直接作为数组塞进这一篇博客的“文档”里**，只需一次查询就能全部读出来，彻底消除了连接操作！

- **3. 查（Find）—— 重点！**
  - 全表查询：`db.student.find()`。
  - 条件查询（Where）：`db.student.find({sname: 'zhangsan'})`。

- **5. 删（Remove/Drop）**：

### 🔥 冲刺讲义：第11章 键值数据库 Redis 速成提纲

#### 🌟 模块一：Redis 到底是个啥？（核心特征必背）

Redis 是一款开源的高性能**键值（Key-Value）**数据库。考试遇到它的特点，默写以下几点必得分：

- **天下武功唯快不破（内存存储）**：它的数据全部存在**内存**中，读写速度远超传统磁盘数据库，普通电脑1秒内能读写超10万个键值。
- **吃“后悔药”（持久化）**：虽然存在内存，但它支持把数据保存在**磁盘**中，重启电脑时能再次加载回来，不会断电就全丢。
- **多面手（丰富的数据类型）**：支持 String（字符串）、Hash（散列）、List（列表）、Set（集合）、Zset（有序集合）等丰富的数据结构。
- **自动销毁（生命周期）**：可以为数据设置“生存时间”（TTL），时间一到自动删除，内存满了还能自动淘汰不需要的数据，所以极度适合做**缓存**。
- **C语言编写**：底层代码只有几万行，轻量且极易与各种编程语言（如Java、Python）交互。

#### ⚔️ 模块二：应用场景（考简答题的重灾区）

什么时候该用 Redis？记住这四大高频场景：

1. **做缓存（Cache）**：查数据时先查 Redis，没有再去传统数据库查，查完顺手存入 Redis。专门用来存账号密码等不常变动、但频繁读取的数据。
2. **短视频/推文“点赞数”统计**：瞬间几万个赞如果直接写进传统数据库，系统会崩溃。用 Redis 在内存里做“加1”操作极快，等夜深人静没压力了，再定时同步到关系型数据库（这叫“数据落地”）。
3. **朋友圈点赞详情**：不仅算总数，还能记录“谁给谁点了赞”。
4. **首页热门推荐**：高频访问的推荐内容直接存入 Redis，千万人点击也不怕。

#### 🛠️ 模块三：环境配置与避坑（实验题考点）

- **防丢配置**：安装后，一定要打开 `redis.conf` 文件，把 `appendonly no` 改成 `**appendonly yes**`，这样重启才不会丢数据。
- **启动命令**：服务端用 `redis-server redis.conf` 启动；客户端用 `redis-cli.exe -h 127.0.0.1 -p 6379` 连上，**默认端口必背：6379**。
- **中文乱码**：如果存了中文，启动客户端时要在后面加一个小尾巴 `**--raw**`。

#### 💻 模块四：五大数据结构与核心命令（必考代码题！）

这里不分大小写，但**务必掌握增删改查的基本命令**！

**1. 通用保命命令**：

- `KEYS *`（查看所有键）。
- `EXISTS key`（查存不存在）、`DEL key`（删除）。
- `EXPIRE key 20`（设置20秒后销毁）、`TTL key`（看还剩几秒活头）。

**2. String（字符串）—— 最基础的玩法**：

- 不仅能存字符，还能存整数（能自增自减），最大不超过 512MB。
- **重要套路：关系型表怎么转 Redis 键？** $\rightarrow$ 格式公式：`**表名:主键值:列名**`。比如，李勇学号95001，录入姓名的命令是：`SET Student:95001:Sname 李勇`。
- **命令**：`SET`（增/改）、`GET`（查）、`MSET/MGET`（批量增/查）。

**3. Hash（散列）—— 拯救局部修改的神器**：

- **痛点**：如果你用 String 存一串 JSON `{name:"zhangsan", age:22}`，想把年龄改成21岁，就得把整个长字符串替换掉，极其麻烦。
- **解决**：Hash 就像 Java 里的 HashMap，把字段拆开存。
- **命令（带H开头）**：`HSET xmu:student:1 age 21`（单独改年龄）、`HGET`（单查）、`HGETALL`（查所有属性）、`HKEYS / HVALS`（只看字段名 / 只看值）。

**4. List（列表）—— 双向排队**：

- 有序、**允许元素重复**，像一个双向链表，两头进出快，中间查得慢。
- **命令（分左右L/R）**：`LPUSH` / `RPUSH`（从左/右塞入）、`LPOP` / `RPOP`（从左/右弹出）、`LRANGE`（看一段范围的元素）。

**5. Set（集合）—— 数学运算大师**：

- 无序、**元素绝对不重复**，查找极快。
- **牛逼功能**：天生支持求交集（`SINTER`）、并集（`SUNION`）、差集（`SDIFF`）。**（比如：算两个用户的“共同好友”，用交集 SINTER 一秒搞定！）**
- **命令（带S开头）**：`SADD`（添加）、`SMEMBERS`（看全部）、`SREM`（移除）、`SISMEMBER`（判断某人是否在集合里）、`SCARD`（看有几个人）。

#### ☕ 模块五：用 Java 连 Redis

如果用 Java 编程操作，最主流的工具包叫 `**Jedis**`（需要导入相关 jar 包）。

- 建立连接的语法：`Jedis jedis = new Jedis("localhost", 6379);`。然后就可以像用 Java 方法一样直接调用 `jedis.hset()` 等方法了。

### 🔥 冲刺讲义：第12章 云数据库 速成提纲

#### 🌟 模块一：为什么要有云数据库？（必考对比分析题！）

云数据库，顾名思义，就是**部署和虚拟化在云计算环境中的数据库**。它本质上**不是一种全新的数据库模型（底层依然可以是关系型或NoSQL），而是一种全新的“服务方式”**。

考试极爱考**传统自建数据库 vs 云数据库**的区别，记住以下几个痛点对比，简答题直接拿满分：

- **成本与付费**：传统方式要花巨资盖机房、买设备；云数据库**零成本投入**，按需付费，用多少给多少。
- **维护负担**：传统方式要自己花钱请专业IT人员天天盯着；云数据库**由云厂商的专业团队7×24小时包揽全部维护**。
- **资源伸缩（最核心优势！）**：传统方式容量是死的，业务暴增时撑不住，业务少时机器闲置浪费；云数据库能提供**近乎无限的资源，一键动态扩容，随时退订**。

#### ⚔️ 模块二：各大门派的云产品（连线/填空题重灾区）

世界上牛气冲天的互联网巨头都有自己的云数据库，必须把它们的名字对号入座：

1. **Amazon（亚马逊）**：云数据库的老大哥。它有关系型的 `Amazon RDS`，有键值型的 `SimpleDB`，还有NoSQL型的 `DynamoDB`。
2. **Google（谷歌）**：代表产品是 `**Google Cloud SQL**`，底层用的是大家最熟悉的 MySQL。
3. **Microsoft（微软）**：代表产品是 `**SQL Azure**`，底层是自家的 SQL Server，支持 TSQL 和存储过程。
4. **🔥** **国产之光 Alibaba（阿里）**：代表产品是 `**PolarDB**`。为了扛住天猫双11像太平洋一样的海量并发，阿里自研了它。目前阿里云已挺进全球权威的Gartner数据库魔力象限的**领导者（Leaders）阵营**，与国外巨头同台竞技毫不逊色。

#### 🏛️ 模块三：核心架构剖析 —— UMP系统是怎么运转的？

UMP（低成本、高性能的MySQL云数据库方案）是本章的硬核技术点。整个系统里有几个关键角色，请务必分清“谁在干什么活”：

- **Zookeeper（大管家/监工）**：负责全局配置、提供分布式锁（选出一个“总管”），并**监控所有底层数据库实例是否活着**。
- **Controller（调度中心）**：系统的“总管”，负责维护“路由表”（记录哪个用户对应哪个后端的数据库机器），处理故障恢复和备份扩容。
- **Proxy（前台大堂经理）**：直接面向用户的代理服务器。用户把SQL请求发给它，它负责**把请求路由（分发）给后端的机器**，还能顺手做资源限制和日志记录。
- **Agent（基层打工人）**：部署在真实物理机上的服务，直接**管理具体的MySQL实例**，执行主从切换和备份任务。
- **RabbitMQ（通信邮差）**：一个工业级的消息队列，系统中各个节点不用直接连线，全靠它来传纸条（消息传送）。

#### 🛡️ 模块四：云数据库的“七大神功”（简答题压轴考点！）

UMP系统结合了这么多组件，到底实现了哪些牛逼的功能？**（重点背诵前四个）**

1. **容灾（不死之身）**：系统会给每个用户建一个“主库”和一个“从库”。Zookeeper 一旦发现主库死机，立刻通知 Controller 修改路由表，并让 Proxy 把用户的请求瞬间切换到从库上，**整个过程对用户完全透明，用户根本感觉不到死机**。
2. **读写分离**：用户发来写操作（增删改），Proxy自动扔给主库处理；发来读操作（查询），Proxy自动均衡地扔给主库和从库处理，减轻单台机器压力。
3. **分库分表**：把一张超级大表拆到多台机器上。Proxy会偷偷帮你把一条SQL语句改写成多条子语句，发给不同的机器，然后把结果合并好再交给你。
4. **资源隔离（防止多租户打架）**：同一台物理机上住了很多用户，怎么防他们抢资源？一是通过 **Cgroup** 限制每个MySQL进程的最大CPU和内存；二是如果某人请求太猛，**Proxy 前台会故意增加延迟来限制他的 QPS（每秒查询率）**。
5. **数据安全机制**：包含 **SSL加密**通信、设置允许访问的 **IP白名单**、记录操作日志，以及 **SQL拦截**（比如拦截危险的 `select *` 全表扫描）。

### 🔥 冲刺讲义：第13章 数据仓库与数据湖 速成提纲

#### 🌟 模块一：数据仓库（Data Warehouse）—— 精装的“图书馆”

传统数据库是用来做“事务处理”的（比如日常记账，要求快进快出），而数据仓库是用来做**“分析和管理决策”**的。

**1. 必背四大特征**：

- **面向主题**：不按流水账记，而是按老板关心的“主题”（如销售额、退货率）来组织数据。
- **集成**：数据从四面八方的破旧系统里抽出来，经过清洗、统一格式后才能放进去。
- **相对稳定**：里面的数据一般**不可更新**，只用来查，不能随便改。
- **反映历史变化**：它会定期给数据拍“快照”，保存1月、2月、3月的历史变化，方便看趋势。

**2. 核心架构**：它由4个部分组成，分别是数据源、数据存储和管理（含ETL提取和数据集市）、**OLAP（联机分析处理）服务器**、以及前端的各类分析查询工具。

**3. 必考对比（数据库 vs 数据仓库）**：

- 数据库：擅长事务处理，数据是最新状态，频繁进行**单行**的读写，高度标准化。
- 数据仓库：擅长分析和大数据报告，**批量写入**，为了查询快，通常采用**列式存储**。

#### 📈 模块二：数据仓库的“五段进化史”

数据仓库不是一天建成的，它经历了五个发展阶段（考试常考排序或特征匹配）：

1. **报表阶段**：最早期，以批处理为主，把数据集中起来看过去发生了什么。
2. **分析阶段**：加入OLAP和数据挖掘，进行即席查询，探究“为什么发生”。
3. **预测阶段**：引入分析模型和机器学习，预测“将来会发生什么”。
4. **实时决策阶段**：传统数仓是批处理，这里变成了**连续更新/短查询**，系统能在战术上提供实时响应。
5. **主动决策阶段**：引入基于事件的触发机制，**系统自动决策**，无需或减少人的参与。

#### 🌊 模块三：数据湖（Data Lake）—— 原始的“大水库”

**1. 什么是数据湖？**

企业不想丢掉任何数据，于是搞了个池子，把结构化数据（表格）、半结构化数据（日志/JSON）甚至**非结构化数据（图片、视频、邮件）统统以“原汁原味”的原始格式囤起来，方便日后“沙中淘金”**。

**2. 湖的本质**：它不是单一产品，而是**“数据存储架构 + 数据处理工具”**。

- 存储底座通常用便宜的云对象存储（如Amazon S3）。
- **🔥** **必考避坑点**：如果只往里倒数据不管理，数据湖就会变成垃圾堆，叫作**“数据沼泽”**！所以必须配备数据目录编制、ETL、安全访问等工具（如Amazon Lake Formation）来管理它。

**3. 神级考点（数据仓库 vs 数据湖的对比）**：

- **数据类型**：数仓只存“结构化”数据；数据湖存“所有类型”数据（结构/半结构/非结构）。
- **Schema（模式）**：数仓是**写之前（实施前）**就要设计好结构；数据湖是**读的时候（分析时）**才去编写结构。
- **谁来用**：数仓主要是**业务分析师**用来看BI报表；数据湖主要是**数据科学家、开发人员**用来跑机器学习。
- **成本**：数仓起步成本极高；数据湖起步成本低（存算分离）。

#### 🛸 模块四：终极形态 —— 湖仓一体（Lake House）

**1. 为什么要湖仓一体？**

因为它们都有致命缺点！数据湖虽然起步便宜，但随着业务规模变大，总体成本（TCO）会飙升；数据仓库则是前期太贵。为了不重复花钱，工程师把它们打通了，**让数据“自由流动”**。湖里的新鲜数据可以直接流到仓里做分析，仓里用完的冷数据退回到湖里便宜保存。

**2. 湖仓一体的六大牛逼特性（简答题杀手）**：

- **事务支持**：它居然能像数据库一样支持ACID事务，保证并发读写不出错。
- **数据治理**：支持星型、雪花型等数仓模型架构。
- **BI支持**：可以直接在源数据上用BI工具查，无延迟。
- **存算分离**：存储和计算分开，扩展能力极强。
- **开放性**：采用开放标准格式（如Parquet），Python、R语言可以直接访问。
- **支持多种数据类型**：结构、半结构、非结构通吃。

### 🔥 冲刺讲义：第14章 SQL与大数据 速成提纲

#### 🌟 模块一：Hadoop上的数据仓库 —— Hive（必考对比题！）

Hive 是构建在Hadoop顶层的数据仓库工具，它定义了一门极其类似SQL的查询语言——**HiveQL**。

- **底层干活的是谁？** Hive本身不存数据也不算数据，它**依赖 HDFS 来存储海量数据，依赖 MapReduce 来进行高性能计算**。你只要写一句简单的HiveQL，底层会自动转换成复杂的MapReduce任务去执行。
- **核心搭档（各司其职）**：Hive专门负责做历史报表分析（静态数据），而如果你需要“实时访问”数据，那就要请出它的老搭档 **HBase** 来互补了。
- **⚔️** **终极必考：Hive vs 传统关系数据库**：
  - **数据更新**：传统库支持随时修改；Hive **不支持更新**，因为数据仓库里存的都是历史静态数据。
  - **执行延迟**：传统库一秒出结果；Hive的延迟很高（能达到分钟级），不适合着急的在线业务。
  - **扩展性**：传统库很难横向加机器；Hive天生基于集群，**扩展性极好**。

#### ⚡ 模块二：内存计算王者 —— Spark SQL

传统Hadoop的MapReduce虽然稳，但总是把数据写在磁盘上，实在太慢了，于是诞生了**基于内存计算**的大数据框架 Spark。

- **辉煌战绩**：Spark在2014年打破了Hadoop保持的基准排序纪录，只用十分之一的计算资源，就跑出了比Hadoop快3倍的速度！
- **Spark全家桶（生态系统）**：它不仅有管大数据的 Spark Core 和 Spark SQL，还包揽了流计算（Spark Streaming）、机器学习（MLlib）和图计算（GraphX）。
- **Spark SQL 为什么会诞生？** 它的前身叫 **Shark**（直接把Hive的任务换成了Spark跑）。后来由于兼容等问题，重构并推出了 Spark SQL。它的核心价值在于填补了技术鸿沟：**把传统SQL查询结构化数据的能力，与复杂的机器学习和高级分析算法完美融合在了一起**。

#### 🌊 模块三：流计算大师 —— Flink SQL

如果说Spark是批处理的王者，那 Flink 就是为了**实时流处理**而生的顶级框架。

- **核心特性**：Flink 支持**批流一体化**、拥有精密的状态管理，还能保证“精确一次”的状态一致性保障，可以横向扩展到数千核心与TB级的状态。目前国内阿里、美团等大厂都在大规模使用它作为分布式引擎。
- **Flink SQL 的作用**：为了让大家不用写复杂的流处理代码，它提供了一套符合标准语义的SQL开发语言。底层依靠 **Apache Calcite** 框架帮你解析SQL，并自动在语法规则层面进行性能优化。

#### 🦅 模块四：HBase的专属“翻译官” —— Phoenix

- **它是谁？** Phoenix 就像是一个内嵌在 HBase 中的 JDBC 驱动，是一个专门为 HBase 构建的 SQL 层。
- **有什么用？** HBase 本来只能通过复杂的API去查数据，但有了 Phoenix，你就可以直接使用**标准的 SQL 语句**去操作 HBase 了。系统会自动把你的 SQL 翻译成一个或多个 HBase Scanner 并行执行，查询性能远超上一代的 Hive！

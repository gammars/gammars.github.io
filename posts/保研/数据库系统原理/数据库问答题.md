## 1. 数据库范式 (1NF, 2NF, 3NF)

### 问：什么是范式？
**答：** 范式是关系数据库设计时用来减少数据冗余、避免插入异常、删除异常、修改异常的一组规则。范式越高，表设计越规范，但查询时可能需要更多连接。

> **背诵：** 范式的核心目标是减少冗余，避免更新异常。

### 问：第一范式 (1NF) 是什么？
**答：** 第一范式要求表中每个属性都是不可再分的原子值，不能在一个字段里存多个值。

- **不符合 1NF 示例：**
    - `学生表(学号, 姓名, 电话)`，其中电话字段值为 `"138xxx, 139xxx"`（一个字段存了多个电话）。
- **符合 1NF 示例：**
    - `学生表(学号, 姓名)`
    - `学生电话表(学号, 电话)`

> **背诵：** 1NF 要求属性原子化，不能一个格子塞多个值。

### 问：第二范式 (2NF) 是什么？
**答：** 第二范式建立在 1NF 的基础上，要求每个非主属性都必须完全依赖于候选键，不能只依赖候选键的一部分。它主要解决“部分函数依赖”问题。

- **不满足 2NF 示例：**
    - `选课表(学号, 课程号, 学生姓名, 课程名, 成绩)`，主键为 `(学号, 课程号)`。
    - 问题：
        - `学号 → 学生姓名`（部分依赖）
        - `课程号 → 课程名`（部分依赖）
- **拆分为 2NF：**
    - `学生表(学号, 学生姓名)`
    - `课程表(课程号, 课程名)`
    - `选课表(学号, 课程号, 成绩)`

> **背诵：** 2NF 解决非主属性对联合主键的部分依赖。

### 问：第三范式 (3NF) 是什么？
**答：** 第三范式建立在 2NF 的基础上，要求非主属性不能传递依赖于候选键。也就是说，不能出现：`主键 → 非主属性A → 非主属性B`。

- **不满足 3NF 示例：**
    - `学生表(学号, 姓名, 学院号, 学院名)`。
    - 问题：`学号 → 学院号 → 学院名`，存在传递依赖。
- **拆分为 3NF：**
    - `学生表(学号, 姓名, 学院号)`
    - `学院表(学院号, 学院名)`

> **背诵：** 3NF 解决非主属性之间的传递依赖。

### 问：1NF、2NF、3NF 分别解决什么问题？
**答：**
- **1NF**：解决字段不原子的问题。
- **2NF**：解决联合主键中的部分依赖问题。
- **3NF**：解决非主属性之间的传递依赖问题。

> **最简背诵：**
> 1.  **1NF**：字段不可再分。
> 2.  **2NF**：非主属性完全依赖主键。
> 3.  **3NF**：非主属性不能依赖其他非主属性。

## 2. SQL 查询语句

### 问：SQL 查询语句的基本格式是什么？
**答：**
```sql
SELECT 列名
FROM 表名
WHERE 条件
GROUP BY 分组列
HAVING 分组后的条件
ORDER BY 排序列;
```

> **背诵顺序：**
> `SELECT` 查什么 → `FROM` 从哪查 → `WHERE` 查哪些行 → `GROUP BY` 怎么分组 → `HAVING` 分组后筛选 → `ORDER BY` 怎么排序

### 问：SQL 的实际执行顺序是什么？
**答：** 虽然 SQL 写法以 `SELECT` 开头，但数据库实际执行顺序大致为：
`FROM` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY` → `LIMIT`

> **背诵：** 先找表，再筛行，再分组，再筛组，再选列，再排序。

### 问：WHERE 和 HAVING 有什么区别？
**答：** `WHERE` 是分组前筛选普通行，`HAVING` 是分组后筛选组。

- **示例：** 查询选课人数大于 3 的课程。
    ```sql
    SELECT cno, COUNT(*)
    FROM sc
    GROUP BY cno
    HAVING COUNT(*) > 3;
    ```
    > 不能用 `WHERE COUNT(*) > 3`，因为 `WHERE` 阶段还没有分组统计。

> **背诵：** `WHERE` 管行，`HAVING` 管组；`WHERE` 不能直接用聚合函数，`HAVING` 可以。

### 问：INNER JOIN、LEFT JOIN、RIGHT JOIN 有什么区别？
**答：**
- **INNER JOIN**：只保留两张表都匹配上的记录。
- **LEFT JOIN**：保留左表全部记录，右表没有匹配则补 `NULL`。
- **RIGHT JOIN**：保留右表全部记录，左表没有匹配则补 `NULL`。

- **示例：**
    ```sql
    SELECT s.sno, s.sname, sc.cno, sc.grade
    FROM student s
    LEFT JOIN sc ON s.sno = sc.sno;
    ```
    （这个查询会查出所有学生，即使有些学生没有选课。）

> **背诵：**
> - `JOIN`：只要匹配的。
> - `LEFT JOIN`：左边全要。
> - `RIGHT JOIN`：右边全要。

### 问：GROUP BY 一般怎么用？
**答：** `GROUP BY` 用来按某个字段分组，通常和 `COUNT`、`SUM`、`AVG`、`MAX`、`MIN` 等聚合函数一起使用。

- **示例 1：** 查询每门课的平均分。
    ```sql
    SELECT cno, AVG(grade)
    FROM sc
    GROUP BY cno;
    ```
- **示例 2：** 查询平均分大于 80 的课程。
    ```sql
    SELECT cno, AVG(grade)
    FROM sc
    GROUP BY cno
    HAVING AVG(grade) > 80;
    ```

### 问：子查询中的 IN 和 EXISTS 有什么区别？
**答：**
- `IN`：判断某个值是否在一个结果集合里。
- `EXISTS`：判断子查询是否能查出结果（即是否存在）。

- **`IN` 示例：**
    ```sql
    SELECT * FROM student
    WHERE sno IN (SELECT sno FROM sc WHERE cno = 'C01');
    ```
- **`EXISTS` 示例：**
    ```sql
    SELECT * FROM student s
    WHERE EXISTS (SELECT * FROM sc WHERE sc.sno = s.sno);
    ```

> **背诵：** `IN` 看值在不在集合里；`EXISTS` 看子查询有没有结果。

### 问：查询“选修了所有课程的学生”怎么写？
**答：** 这是经典的双重 `NOT EXISTS` 用法。

```sql
SELECT *
FROM student s
WHERE NOT EXISTS (
    SELECT *
    FROM course c
    WHERE NOT EXISTS (
        SELECT *
        FROM sc
        WHERE sc.sno = s.sno
          AND sc.cno = c.cno
    )
);
```
**理解方式：** 不存在这样一门课程：这个学生没有选它。换成人话就是：学生 `s` 选修了所有课程。

> **背诵模板：**
> ```sql
> SELECT * FROM 主体表 x
> WHERE NOT EXISTS (
>     SELECT * FROM 全部对象表 y
>     WHERE NOT EXISTS (
>         SELECT * FROM 关系表 z
>         WHERE z.主体编号 = x.主体编号
>           AND z.对象编号 = y.对象编号
>     )
> );
> ```

## 3. 数据库类型与关系型特点

### 问：数据库有哪些常见类型？
**答：** 常见数据库类型有层次数据库、网状数据库、关系型数据库、面向对象数据库、NoSQL 数据库等。现在最常用的是关系型数据库和 NoSQL 数据库。

- **关系型数据库代表：** MySQL、PostgreSQL、Oracle、SQL Server。
- **NoSQL 代表：** Redis、MongoDB、HBase、Cassandra。

### 问：关系型数据库有什么特点？
**答：** 关系型数据库用二维表组织数据，表由行和列组成。行表示一条记录，列表示一个属性。表和表之间通过主键、外键建立联系。其特点是结构清晰、支持 SQL、支持事务、支持完整性约束、数据一致性强。

> **背诵：** 关系型数据库以二维表存储数据，通过主键和外键建立关系，支持 SQL、事务和完整性约束。

### 问：关系型数据库和 NoSQL 的区别是什么？
**答：**
- **关系型数据库：** 结构固定，数据一致性强，适合银行、订单、教务系统等对事务要求高的场景。
- **NoSQL 数据库：** 结构灵活，扩展性强，适合缓存、日志、社交动态、大数据等高并发、高扩展场景。

> **背诵：** 关系型数据库重一致性和事务，NoSQL 重灵活性和扩展性。

## 4. 数据库锁类型

### 问：数据库为什么需要锁？
**答：** 数据库在并发访问时，多个事务可能同时读写同一份数据。如果没有锁，就可能出现脏读、不可重复读、丢失修改等问题。锁的作用是控制并发，保证数据一致性。

> **背诵：** 锁是为了解决并发事务同时读写数据时的一致性问题。

### 问：共享锁和排他锁是什么？
**答：**
- **共享锁 (读锁)**：多个事务可以同时加共享锁读取同一数据，但不能修改。
- **排他锁 (写锁)**：一个事务加了排他锁后，其他事务不能再读写这个数据，直到锁释放。

> **背诵：**
> - 共享锁允许多个事务一起读。
> - 排他锁只允许一个事务写，其他事务不能读写。

### 问：行锁和表锁有什么区别？
**答：**
- **行锁：** 锁住某一行数据，粒度小，并发性能好，但加锁开销大。
- **表锁：** 锁住整张表，粒度大，并发性能差，但加锁开销小。

> **背诵：**
> - 行锁：并发高，开销大。
> - 表锁：并发低，开销小。

### 问：乐观锁和悲观锁有什么区别？
**答：**
- **悲观锁：** 认为冲突经常发生，操作前先加锁。
- **乐观锁：** 认为冲突不常发生，先不加锁，提交时再检查数据有没有被修改。常用版本号 (`version`) 或时间戳实现。

- **乐观锁实现示例：**
    ```sql
    UPDATE product
    SET stock = stock - 1,
        version = version + 1
    WHERE id = 1
      AND version = 当前版本号;
    ```
    （如果更新影响行数为 0，说明版本号变了，数据被别人改过。）

> **背诵：**
> - 悲观锁：先锁再操作，适合冲突多。
> - 乐观锁：先操作后检查，适合读多写少。

### 问：InnoDB 中有哪些常见锁？
**答：** InnoDB 常见锁包括行锁、表锁、共享锁、排他锁、意向锁、记录锁、间隙锁、临键锁。

- **记录锁：** 锁住已有记录。
- **间隙锁：** 锁住两个索引值之间的范围，防止别人插入。
- **临键锁：** `记录锁 + 间隙锁`，主要用于防止幻读。

> **背诵：** InnoDB 通过记录锁、间隙锁、临键锁解决并发修改和幻读问题。

## 5. 三大完整性约束

### 问：数据库的三大完整性约束是什么？
**答：** 实体完整性、参照完整性、用户自定义完整性。

> **背诵：**
> - **实体完整性：** 主键不能为空且唯一。
> - **参照完整性：** 外键必须引用已存在的主键，或者为空。
> - **用户自定义完整性：** 根据业务规则限制数据。

### 问：实体完整性是什么？
**答：** 实体完整性要求每张表中的每条记录都能被唯一标识，通常通过主键实现。主键不能为空，也不能重复。

- **示例：**
    ```sql
    CREATE TABLE student (
        sno CHAR(10) PRIMARY KEY,
        sname VARCHAR(20)
    );
    ```

### 问：参照完整性是什么？
**答：** 参照完整性要求外键的值必须来自被引用表中的主键值，或者为空。它保证表与表之间的引用关系正确。

- **示例：**
    ```sql
    CREATE TABLE sc (
        sno CHAR(10),
        cno CHAR(10),
        grade INT,
        FOREIGN KEY (sno) REFERENCES student(sno)
    );
    ```
    （表示 `sc` 表中的 `sno` 必须是 `student` 表中已经存在的 `sno`。）

### 问：用户自定义完整性是什么？
**答：** 用户自定义完整性是根据具体业务设置的约束，比如年龄不能小于 0，成绩必须在 0 到 100 之间，性别只能是男或女。

- **示例：**
    ```sql
    CREATE TABLE sc (
        grade INT CHECK (grade >= 0 AND grade <= 100)
    );
    ```

## 6. 事务与锁、ACID 特性

### 问：什么是事务？
**答：** 事务是数据库中一组操作的集合，这组操作要么全部成功，要么全部失败，不能只执行一部分。例如银行转账（A 账户扣 100 元，B 账户加 100 元）必须作为一个整体。

> **背诵：** 事务是一组不可分割的数据库操作，要么全部提交，要么全部回滚。

### 问：事务的 ACID 是什么？
**答：**
- **原子性 (Atomicity)：** 事务要么全做，要么全不做。
- **一致性 (Consistency)：** 事务执行前后数据库都必须处于正确状态。
- **隔离性 (Isolation)：** 并发事务之间不能互相干扰。
- **持久性 (Durability)：** 事务提交后结果要永久保存，即使系统崩溃也不能丢失。

> **背诵：**
> - **原子性：** 要么全做，要么全不做。
> - **一致性：** 执行前后数据合法。
> - **隔离性：** 并发事务互不干扰。
> - **持久性：** 提交之后永久生效。

### 问：事务和锁有什么关系？
**答：** 事务保证一组操作的正确性，锁保证多个事务并发执行时不会互相破坏。事务需要依靠锁、日志和并发控制机制来实现 ACID。

> **背诵：** 事务解决操作整体性，锁解决并发隔离性。

### 问：事务隔离级别有哪些？
**答：** 常见隔离级别有四种（从低到高）：
1.  **读未提交：** 可能发生脏读、不可重复读、幻读。
2.  **读已提交：** 避免脏读，但可能发生不可重复读、幻读。
3.  **可重复读：** 避免脏读和不可重复读（MySQL InnoDB 默认），一般还能通过 MVCC 和临键锁解决幻读。
4.  **串行化：** 隔离性最强，事务串行执行，并发性能最低。

> **背诵：** 读未提交最低，串行化最高。隔离性越强，并发性能越差。

### 问：脏读、不可重复读、幻读是什么？
**答：**
- **脏读：** 一个事务读到了另一个事务还没提交的数据。
- **不可重复读：** 同一个事务中，两次读取同一行数据，结果不一样（因为中间被别人修改并提交了）。
- **幻读：** 同一个事务中，两次范围查询，结果行数不一样（因为中间别人插入或删除了符合条件的数据）。

> **背诵：**
> - **脏读：** 读到未提交。
> - **不可重复读：** 同一行前后不一样。
> - **幻读：** 同一范围前后多了或少了行。

## 7. 存储过程与触发器

### 问：什么是存储过程？
**答：** 存储过程是一组预先编译好并保存在数据库中的 SQL 语句，可以通过调用来执行。它适合封装重复的业务逻辑。

- **示例：**
    ```sql
    CREATE PROCEDURE query_student_by_dept
        @dept VARCHAR(20)
    AS
    BEGIN
        SELECT * FROM student WHERE sdept = @dept;
    END;
    -- 调用：EXEC query_student_by_dept 'CS';
    ```

> **背诵：** 存储过程是保存在数据库中的一组 SQL 程序，可以被反复调用。

### 问：存储过程有什么优点？
**答：**
1.  减少重复 SQL，提高代码复用性。
2.  减少客户端和数据库之间的数据传输。
3.  封装业务逻辑。
4.  配合权限控制提高安全性。

> **背诵：** 存储过程的优点是封装逻辑、提高复用、减少传输、增强安全。

### 问：什么是触发器？
**答：** 触发器是当某个数据库事件 (`INSERT`, `UPDATE`, `DELETE`) 发生时自动执行的一段程序。

- **示例：** 插入成绩时检查成绩范围。
    ```sql
    CREATE TRIGGER check_grade_insert
    ON sc
    AFTER INSERT
    AS
    BEGIN
        IF EXISTS (SELECT * FROM inserted WHERE grade < 0 OR grade > 100)
        BEGIN
            ROLLBACK;
        END
    END;
    ```

> **背诵：** 触发器是由数据库事件自动触发执行的程序。

### 问：存储过程和触发器的区别是什么？
**答：**
- **存储过程：** 需要用户**主动调用**，主要用于封装业务操作。
- **触发器：** 由 `INSERT`、`UPDATE`、`DELETE` 等事件**自动触发**，主要用于自动维护约束、日志、审计、级联更新等。

> **背诵：**
> - 存储过程是主动调用。
> - 触发器是事件自动触发。

## 8. REDO / UNDO 机制

### 问：为什么数据库需要日志？
**答：** 数据库需要日志是为了保证事务的原子性和持久性。事务执行过程中，如果系统崩溃，数据库可以通过日志恢复到正确状态。

> **背诵：** 日志用于故障恢复，保证事务的原子性和持久性。

### 问：REDO 日志是什么？
**答：** REDO 日志（重做日志）用来保证事务的持久性。事务提交后，即使数据页还没真正写入磁盘，只要 REDO 日志已经落盘，系统崩溃后也可以根据 REDO 日志重新执行修改，把已提交事务的结果恢复出来。

> **背诵：** REDO 保证已提交事务不丢失。

### 问：UNDO 日志是什么？
**答：** UNDO 日志（回滚日志）用来保证事务的原子性。如果事务执行失败或主动回滚，数据库可以根据 UNDO 日志把数据恢复到修改前的状态。此外，UNDO 还可以用于 MVCC，让不同事务读到合适版本的数据。

> **背诵：** UNDO 用来回滚未提交事务，也支持 MVCC。

### 问：REDO 和 UNDO 的区别是什么？
**答：**
- **REDO：** 记录“修改后的值”，用于崩溃恢复时重做已提交事务。
- **UNDO：** 记录“修改前的值”，用于事务回滚和 MVCC。

> **背诵：**
> - REDO：重做，保证持久性。
> - UNDO：撤销，保证原子性。

### 问：数据库崩溃恢复时 REDO 和 UNDO 怎么用？
**答：** 系统崩溃后，数据库会根据日志判断哪些事务已经提交，哪些事务没有提交。
- 已经提交但数据没完全写入磁盘的事务，需要 **REDO**。
- 没有提交的事务，需要 **UNDO**。

> **背诵：**
> - 已提交没写完，用 REDO 补上。
> - 未提交写了一半，用 UNDO 撤回。

## 9. MySQL 存储引擎对比

### 问：MySQL 存储引擎是什么？
**答：** 存储引擎是 MySQL 中真正负责数据存储、索引管理、事务处理、锁机制的模块。不同存储引擎有不同特点。

> **背诵：** 存储引擎决定表的数据怎么存、索引怎么建、事务和锁怎么实现。

### 问：InnoDB 和 MyISAM 有什么区别？
**答：**
- **InnoDB：** 支持事务、支持外键、支持行级锁，崩溃恢复能力强，适合高并发和对数据一致性要求高的业务，是 MySQL 默认存储引擎。
- **MyISAM：** 不支持事务、不支持外键，主要使用表级锁，查询速度在某些场景下较快，但崩溃恢复和并发写能力较弱。

> **背诵：**
> - InnoDB 支持事务、外键、行锁，适合高并发。
> - MyISAM 不支持事务和外键，主要是表锁，适合读多写少。

### 问：为什么现在一般用 InnoDB？
**答：** 因为大多数业务系统都需要事务、并发控制、崩溃恢复和数据一致性。InnoDB 支持 ACID、MVCC、行锁、外键和崩溃恢复，因此更适合现代业务系统。

> **背诵：** 现代业务重一致性和并发，所以默认选 InnoDB。

### 问：MEMORY 存储引擎是什么？
**答：** MEMORY 存储引擎把数据放在内存里，访问速度快，但数据库重启后数据会丢失，适合临时数据或缓存场景。

> **背诵：** MEMORY 快，但断电丢数据。

## 10. 数据库优化方法

### 问：数据库优化可以从哪些方面入手？
**答：** 可以从 SQL 优化、索引优化、表结构优化、事务优化、缓存优化、架构优化几个方面入手。

> **背诵：** SQL 写得好，索引建得准，表结构设计合理，事务尽量短，热点数据用缓存，压力大时做分库分表和读写分离。

### 问：SQL 优化有哪些方法？
**答：**
1.  尽量避免 `SELECT *`，只查需要的列。
2.  `WHERE` 条件尽量使用索引列。
3.  避免在索引列上使用函数或表达式。
4.  避免 `LIKE '%xxx'` 这种前导模糊匹配。
5.  避免大事务和复杂嵌套子查询。
6.  用 `JOIN` 时要保证连接字段有索引。
7.  用 `EXPLAIN` 查看执行计划。

> **背诵：** 少查列，少查行，用索引，避函数，避前模糊，看 EXPLAIN。

### 问：表结构怎么优化？
**答：**
1.  字段类型尽量选择合适且较小的类型（如能用 `INT` 不用 `BIGINT`，能用 `VARCHAR` 不用 `TEXT`）。
2.  经常一起查询的数据可以放在同一张表。
3.  冗余字段要谨慎使用，必要时可以用适度反规范化提高查询效率。
4.  冷热数据可以分离，大表可以分区或分表。

> **背诵：** 表结构优化就是字段合适、减少冗余、冷热分离、大表拆分。

### 问：事务怎么优化？
**答：**
1.  事务要尽量短，避免在事务中执行耗时操作。
2.  更新数据时尽量按固定顺序访问，减少死锁。
3.  只在必要时开启事务。
4.  合理选择隔离级别。

> **背诵：** 事务越短，锁持有时间越短，并发性能越好。

### 问：架构层面怎么优化？
**答：**
1.  使用缓存减轻数据库压力。
2.  使用主从复制实现读写分离。
3.  数据量特别大时可以分库分表。
4.  对历史数据归档。
5.  对热点数据做缓存或异步处理。

> **背诵：** 单机扛不住就缓存、读写分离、分库分表、异步削峰。

## 11. 何时使用索引

### 问：索引是什么？
**答：** 索引是数据库为了加快查询速度建立的数据结构。它类似书的目录，可以帮助数据库快速定位数据，而不是全表扫描。

> **背诵：** 索引就是数据库的目录，用空间换时间。

### 问：索引有什么优点和缺点？
**答：**
- **优点：** 提高查询、排序、分组、连接的速度。
- **缺点：** 占用额外存储空间，并且 `INSERT`、`UPDATE`、`DELETE` 时需要维护索引，会降低写入性能。

> **背诵：** 索引提高查询速度，但占空间，并降低写入速度。

### 问：哪些字段适合建索引？
**答：**
1.  经常出现在 `WHERE` 条件中的字段。
2.  经常用于 `JOIN` 连接的字段。
3.  经常用于 `ORDER BY`、`GROUP BY` 的字段。
4.  区分度高的字段（如手机号、身份证号、学号）。

> **背诵：** `WHERE`、`JOIN`、`ORDER BY`、`GROUP BY` 常用字段适合建索引。区分度越高，越适合建索引。

### 问：哪些字段不适合建索引？
**答：**
1.  数据量很小的表。
2.  区分度很低的字段（如性别、是否删除）。
3.  经常更新的字段。
4.  很少作为查询条件的字段。

> **背诵：** 表太小不用建，区分度低不建，经常改少建，不常查不建。

### 问：为什么性别字段不适合建索引？
**答：** 因为性别字段区分度低，通常只有男、女两种值。即使建索引，也可能一次查出大量数据，数据库还要回表，效率不一定比全表扫描高。

> **背诵：** 区分度低的字段建索引效果差。

## 12. 如何使用索引

### 问：MySQL 常见索引结构是什么？
**答：** MySQL InnoDB 常用 B+ 树索引。B+ 树高度低，叶子节点有序并且通过链表相连，适合范围查询和排序。

> **背诵：** InnoDB 索引主要是 B+ 树，适合等值查询、范围查询和排序。

### 问：主键索引和普通索引有什么区别？
**答：**
- **主键索引（聚簇索引）：** 叶子节点直接存放整行数据。
- **普通索引（二级索引）：** 叶子节点存放主键值。如果通过普通索引查到主键后，还需要再去主键索引中查整行数据，这叫**回表**。

> **背诵：**
> - 主键索引叶子节点存整行数据。
> - 普通索引叶子节点存主键值，可能需要回表。

### 问：什么是回表？
**答：** 通过普通索引查到主键值后，再根据主键去主键索引中查询完整记录，这个过程叫回表。

- **示例：**
    ```sql
    SELECT * FROM student WHERE name = '张三';
    ```
    （如果 `name` 上有普通索引，数据库先通过 `name` 索引找到主键，再根据主键查整行数据，这就是回表。）

> **背诵：** 二级索引查到主键后，再查整行数据，叫回表。

### 问：什么是覆盖索引？
**答：** 如果查询需要的字段都能从索引中直接拿到，就不需要回表，这叫覆盖索引。

- **示例：** 有联合索引 `INDEX idx_name_age(name, age)`。
    ```sql
    SELECT name, age FROM student WHERE name = '张三';
    ```
    （只需要 `name` 和 `age`，这两个字段都在索引里，所以不需要回表。）

> **背诵：** 查询字段都在索引里，不用回表，就是覆盖索引。

### 问：什么是联合索引？
**答：** 联合索引是在多个字段上建立的索引。

- **示例：**
    ```sql
    CREATE INDEX idx_name_age_class ON student(name, age, class_id);
    ```

### 问：什么是最左前缀原则？
**答：** 联合索引必须从最左边的字段开始连续使用，才能充分利用索引。

- **示例：** 索引为 `(name, age, class_id)`。
    - **可以使用索引的情况：**
        - `WHERE name = '张三';`
        - `WHERE name = '张三' AND age = 20;`
        - `WHERE name = '张三' AND age = 20 AND class_id = 1;`
    - **不能充分使用索引的情况（跳过了最左边的 `name`）：**
        - `WHERE age = 20;`
        - `WHERE class_id = 1;`
        - `WHERE age = 20 AND class_id = 1;`

> **背诵：** 联合索引从左往右连续使用，不能跳过最左列。

### 问：哪些写法会导致索引失效？
**答：** 常见索引失效情况有：
1.  在索引列上使用函数：`WHERE YEAR(create_time) = 2024;`
2.  在索引列上做运算：`WHERE age + 1 = 20;`
3.  使用前导模糊查询：`WHERE name LIKE '%三';`
4.  发生隐式类型转换：`WHERE phone = 123456;`（`phone` 是字符串类型时）
5.  联合索引不满足最左前缀原则。
6.  使用 `OR` 时，两边字段不都具备索引。

> **背诵：** 函数、计算、前模糊、隐式转换、跳过最左列，容易让索引失效。

### 问：如何判断 SQL 有没有用到索引？
**答：** 可以使用 `EXPLAIN` 查看执行计划。

- **示例：**
    ```sql
    EXPLAIN SELECT * FROM student WHERE sno = '001';
    ```
- **重点查看字段：**
    - `key`：实际使用的索引。
    - `rows`：预计扫描的行数，越少越好。
    - `type`：从好到差大致为 `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`。`ALL` 表示全表扫描，通常需要优化。

> **背诵：** 用 `EXPLAIN` 看 `key` 是否用索引，看 `rows` 是否扫描太多，看 `type` 是否为 `ALL`。
